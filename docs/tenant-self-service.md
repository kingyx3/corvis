# Customer tenant self-service

Issue #176 completes the existing tenant-provisioning and invitation flows with customer member management and workspace selection.

Organization Admins open **Access administration** to filter and sort accepted identities by identity, workspace or role. Accepted invitation email is the display label where available; pre-existing identities retain their IdP subject. Invitations remain a separate list with pending/accepted/revoked/expired status. Each active workspace role has **Manage role**, allowing replacement or immediate removal with a required reason and confirmation. Organization Admin grants require a separate explicit confirmation. Self-edits are refused; another Organization Admin must manage the acting user's access. The existing **Deactivate everywhere** flow remains the tenant-wide offboarding action.

`POST /api/v1/access/members/role` accepts `userId`, `workspaceId`, `expectedRole`, `roleName` (null removes that role), `reason`, and `confirmTenantAdmin`. It rechecks the actor's tenant-admin membership, locks the target identity/membership, rejects stale selections, preserves the prior role's expiry and all unrelated memberships, and commits its audit event atomically. Removing the last effective workspace role expires that workspace's resource entitlements. A transport without transaction support fails closed. The response contains the audit event ID; the broader customer audit browser remains tracked under #181/C9.

The sidebar shows the authenticated subject and real workspace/tenant names. Users with multiple active memberships in their current tenant receive a native keyboard-operable workspace selector. Selection is verified against `/api/v1/me` before it is persisted. Signed OIDC/SAML broker sessions may select another workspace within their authenticated tenant; Postgres re-resolves all permissions and entitlements. Service identities cannot change their signed workspace context. Direct OIDC continues to validate selectors and membership through the same authorization repository. This does not introduce cross-tenant discovery or let a browser mutate signed tenant identity.

A successful switch reloads the document, discarding loaded data, modals, selections, searches, analytics and capabilities before the next workspace renders. All customer API adapters—including analytics, exports and uploads—send the selected context. Each loaded page pins its context so an outstanding upload cannot change destination when another tab updates the preference. Other tabs reload on a selection change. Review preferences and resumable upload records are namespaced by workspace. If a saved selection is no longer authorized, **Reset workspace selection** clears it and retries the authenticated default context.

The second demo workspace intentionally has no data and read-only document capabilities, making stale data and permission reuse observable in regression tests. The accessibility surface matrix includes access administration; additional matrix tests cover the selector, role confirmation, focus restoration and reload isolation. Real IdP/Postgres/browser integration and two-tenant evidence still belong to the production-like UAT gates; this implementation does not satisfy those live-evidence gates by itself.

## Hardening notes (SCIM, bulk invite, lifecycle)

- Source-connection governance (`source_connection.create|test|pause|resume|reauthorize|revoke`, target type `source_connection`) writes its audit event in the same transaction as the change, and the tenant access audit listing and its CSV export (`GET /api/v1/access/audit`) include those events. Metadata holds only the provider key or error class, never a credential. This was previously missing from the listing's action filter (#253).
- SCIM requests are rate limited per client address and per targeted tenant before any database lookup (429 with `Retry-After`); the limits are process-local per instance. Minting or rotating the SCIM token writes an `access.scim.configured` audit event in the same transaction (it records the previous settings, never the token) and appears in the tenant access audit. SCIM user creation provisions the identity and the SCIM record atomically, and unexpected SCIM 500s log the error class.
- `POST /api/v1/access/invitations/bulk` no longer confirms `tenant_admin` rows implicitly: those rows fail with `tenant_admin_confirmation_required` unless the request carries `?confirmTenantAdmin=true`. Per-row failures report a stable code, not the raw error message.
- `POST /api/v1/admin/identity-lifecycle` refuses to disable or demote the calling administrator (`cannot_deactivate_current_user`, `cannot_change_current_user`) or the last active tenant administrator (`last_tenant_admin`), all 409. SQL business errors raised by the identity-lifecycle, access-policy and support-access functions map to 4xx instead of 500.
- Upload access remains uploader-or-`admin` (`lib/server/upload-access.ts`). Open product decision: an `accountadmin` of another workspace in the tenant maps to `admin` and can act on any tenant upload.

## Data retention and full data export (F10)

The same page (`/access-self-service`) now shows, for Organization Admins only:

- **Data retention and legal holds**: a read-only table of how long each class of the organization's data is kept, what happens when the contract ends, and any legal hold (matter reference and what it covers). Corvis operations set and lift both; a hold overrides retention. The view hides who placed a hold.
- **Full data export**: an Organization Admin states why the export is needed; a *different* Organization Admin approves (or rejects with a reason) before anything is built, and the requester can withdraw it until the build starts. When built, the export is a checksummed archive (published data, the access audit trail and a source-document inventory) behind a single-use, ten-minute download link. Only data the organization may redistribute under its contracts is included, and the manifest says how many funds and documents were left out. Source document files are not part of the export yet. Every step is audited and appears in the access audit trail.

Demo mode serves both from in-memory stores (a colleague's pending request is seeded so the approval flow can be exercised; the archive is built at the moment of approval from the demo catalog). Contract: `API_CONVENTIONS.md`, "Data retention and full data export (F10)".
