# Corvis production activation

Merged code is not production evidence. This document owns the technical activation checks; Confluence owns the business/control decision to approve production readiness.

## Configuration authority

GitHub Environments hold only external trust roots and genuine environment decisions. Runtime secrets live in GCP Secret Manager. Derived provider identifiers, runtime URLs and internal workload identities are generated by Terraform/workflows rather than copied into GitHub variables.

See [`GITHUB_ENVIRONMENTS.md`](GITHUB_ENVIRONMENTS.md), [`DEPLOYMENT.md`](DEPLOYMENT.md) and [`INFRASTRUCTURE.md`](INFRASTRUCTURE.md).

## Repository-complete before provider activation

The checked-in production-like path now contains the following repository-side boundaries:

- non-bypassable `main` PR/check governance verification compatible with the current solo-maintainer model and future multi-operator approval mode;
- Terraform validation inside the required `frontend` merge check as well as the dedicated Terraform workflow;
- immutable release-image digest/provenance selection;
- Cloudflare Worker -> restricted API key -> Google API Gateway -> dedicated gateway identity -> IAM-private Cloud Run API;
- provider-neutral direct OIDC token verification with Postgres-authoritative membership/roles/rights/session resolution;
- separate IAM-private Cloud Run worker identity/runtime;
- keyless Pub/Sub push, Cloud Tasks retry and Cloud Scheduler outbox dispatch using Google OIDC and an explicit worker audience;
- a single Terraform-owned `corvis-postgres-dsn-${environment}` Secret Manager contract consumed by migration, API, worker and acceptance paths;
- forward-only checksum/ledger-backed Postgres migration execution inside the normal promotion workflow before runtime apply;
- protected/versioned Terraform remote state plus guarded idle/full decommission workflows;
- GCS/KMS source storage, object-level runtime IAM, Artifact Registry cleanup, queue/DLQ primitives and baseline monitoring.

These items still require live provider application to become production-proven.

## Required external/provider bindings

Before a production-like release can operate, the environment still needs:

1. **GCP trust bootstrap** — billed project, `corvis-deploy`, repository/environment-scoped GitHub WIF provider and the deploy IAM required by the checked-in root.
2. **Cloudflare ownership** — authoritative zone and scoped Terraform token for environments where the public API edge is enabled.
3. **Identity provider** — approved OIDC issuer/audience (or a reviewed SAML/identity-broker path). Production OIDC is verified directly; no Corvis assertion proxy is required for the default path.
4. **Supabase/Postgres** — isolated Singapore environment project, TLS-verified runtime DSN written directly into `corvis-postgres-dsn-${environment}`, approved backup posture and provider ownership.
5. **Customer/admin browser surfaces and SSO session integration** — publish only after their distinct runtime/security boundary and approved browser identity flow are implemented; do not manufacture a provider choice in Terraform.
6. **Malware/representation/extraction/retrieval/AI/delivery providers** — only the integrations actually enabled for the UAT/customer journey, with credentials kept out of source control and normal logs.
7. **Monitoring ownership** — real notification recipients/budget ownership where alerts/budgets are enabled.

Snowflake is not a launch dependency unless separately activated as downstream analytics/sharing.

## Promotion sequence

For a production-like environment:

1. bootstrap GCP trust and foundation from GitHub;
2. activate the isolated Postgres provider and write its DSN to Secret Manager;
3. configure the approved OIDC issuer/audience and Cloudflare roots;
4. run **Build release image** from reviewed `main`;
5. run **Terraform deploy** plan;
6. on apply, the workflow verifies the Postgres secret, applies only pending migrations with evidence, applies the exact Terraform plan, and requires public API health through the edge;
7. run **Security acceptance**;
8. only full acceptance advances the environment's known-good digest.

Normal Terraform deploy is not a teardown path. Use `gcp-decommission.yml` for guarded idle/full lifecycle transitions.

## UAT acceptance

UAT must use synthetic or explicitly sanitized data and prove the actual provider topology rather than demo adapters.

### Security and tenancy

- OIDC/session authentication for representative human and service identities;
- Postgres-authoritative membership/role/right/session lifecycle resolution;
- horizontal and vertical authorization negatives across at least two tenants;
- live RLS negatives and service-role privilege tests;
- Cloudflare Worker traversal, TLS/WAF/rate/cache controls and gateway-key bypass negatives;
- direct unauthenticated API and worker Cloud Run rejection plus exact invoker IAM;
- Pub/Sub/Scheduler/Cloud Tasks worker identity/audience wiring;
- no browser/client path capable of manufacturing trusted business identity headers.

### Canonical customer journey

```text
authenticated customer
  -> authorized source upload/connection
  -> GCS validation/quarantine/document registration
  -> durable worker processing
  -> governed review/reconciliation/canonicalization
  -> versioned publication
  -> tenant-safe browse/API
  -> enabled export/webhook delivery
```

Exercise interruption/resume/idempotency, exact GCS lineage, review waiting/resume, duplicate/redelivered work and downstream delivery behavior.

### Failure and recovery

- worker crash/redelivery without duplicate canonical/publication effects;
- persisted retry honoring `nextAttemptAt`;
- terminal dead-letter plus authorized recovery;
- correction replay/republication preserving original immutable history;
- representative non-critical dependency failures with scoped degradation;
- rollback to the last accepted immutable image;
- Postgres backup/restore at the actually purchased recovery tier;
- immutable GCS source inventory/reconciliation after restore;
- representative concurrency/quarter-end load and connection-budget evidence.

### Data/product controls

- malware clean/threat quarantine behavior;
- source/reference lineage completeness;
- search/retrieval authorization negatives;
- deterministic numerical/reconciliation correctness and Ask Corvis citation/prompt-injection evaluations where enabled;
- webhook replay/signature/idempotency and export manifest/checksum/expiry where enabled;
- retention/deletion/legal-hold execution across every enabled authoritative/derived store.

## Release governance pre-flight

Release image builds and Terraform apply read the effective `main` rules and exact release commit checks **before** acquiring provider credentials.

The required GitHub Actions checks are:

- `frontend` — includes lint, TypeScript, unit/build/browser/dependency gates and Terraform formatting/provider validation;
- `container`;
- `rate-limit-postgres`;
- `Analyze TypeScript`;
- `secret-history`;
- `forbidden-artifacts`.

Active applicable rulesets must prohibit deletion/force-push, require PRs with stale-review dismissal, enforce those checks strictly and expose no bypass actors. While Corvis has a single maintainer, zero required approvals is accepted because a mandatory independent review would deadlock the repository. When another operator is added, enable at least one approval plus last-push approval; the release verifier already requires last-push approval whenever approvals are configured.

## Known-good and rollback

`security-acceptance.yml` records the exact accepted digest under the versioned Terraform state bucket only after all required live acceptance jobs pass. Failed/incomplete/skipped mandatory evidence cannot advance known-good state.

Application rollback redeploys that accepted digest. Database migrations remain forward-reviewed; do not silently reverse destructive schema changes. Database restore is an incident-recovery procedure, not routine code rollback.

## Operating evidence before first enterprise customer

At minimum retain current evidence for:

- live tenant/RLS/security acceptance;
- full processing/retry/dead-letter/recovery/replay journey;
- backup/restore and incident exercise;
- representative performance/capacity;
- data-quality correction/republication;
- standard customer implementation/cutover/rollback rehearsal;
- enabled source/export/webhook integrations;
- independent production-equivalent security assessment and closure of launch-blocking findings.

These are tracked by the existing production-readiness issues; do not close them merely because the repository implementation exists.

## Facts source control cannot prove

Source control cannot prove provider ownership/billing, IdP policy, real customer data rights/consent, production backup success, a penetration test, incident response execution, recurring access review or final launch approval. Those remain deliberate external evidence gates. Everything safely automatable after the initial trust roots should flow through the reviewed GitHub path rather than undocumented console work.
